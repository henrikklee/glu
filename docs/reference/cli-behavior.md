# CLI behavior

The exact command reference is generated by the binary. Start with the agent- and human-readable overview:

```sh
glu help
```

Use `glu help --json` only when a machine-readable command manifest is useful.

This document describes the behavior layer above individual flags: rendering, planning, confirmation, and schema integration.

## Design goal

The CLI has many orthogonal choices: human output, JSON output, NUL output, plan mode, tree mode, broad mutations, confirmation, local answers, registry answers, and short flag composition.

The CLI normalizes those choices into predictable contracts:

- one command model;
- consistent renderers;
- explicit mutation planning;
- no scraping of decorated terminal output;
- no silent confirmation in scripts.

## Command model

Clap is the syntax authority. One descriptor tree records product semantics and exposes them through help JSON. Human help, capability checks, dispatch, schemas, and agent-facing metadata all use that tree.

- aliases canonicalize to command identities;
- short flags compose where supported;
- every command declares the global options and output protocols it supports;
- JSON errors preserve invocation context;
- generated contract tests cover every command and global option in the descriptor.

## Output protocols

The command descriptor selects one protocol before glu constructs output:

- `human` for terminal prose, tables, trees, progress, and notices;
- `json_envelope` for one typed result or error document;
- `null_names` for NUL-delimited package names;
- `raw_shell_text` for shell integration;
- `internal_worker` for the captured postinstall worker protocol.

The last two are internal command paths rather than general formatting options. A command rejects a global output option that its descriptor does not support.

### Human

TTY output can use color, layout, progress, hints, prompts, and tree drawing.

Human output optimizes for readability. It is not a stable machine interface.

### JSON

JSON-capable operational commands return one envelope.

Success:

```json
{
  "ok": true,
  "command": "list",
  "result": {}
}
```

Failure:

```json
{
  "ok": false,
  "command": "list",
  "invocation": {
    "argv": ["list", "--bad"],
    "command_path": ["list"],
    "recognized": true
  },
  "error": {
    "code": "parse_error",
    "message": "..."
  }
}
```

Help JSON uses the same success envelope. Its `result` is a compact command manifest; generated result and error schemas are included only when explicitly requested with `--schemas`.

Parse failures and invalid scoped help use `parse_error`. Unsupported options and invalid option combinations use `invalid_flag_combination`. Runtime failures use typed codes for empty declarations, package lookup and metadata requests, registry transport and responses, install phases, partial installs, and interruption. `command_failed` is the fallback when no more specific code is available. The help manifest's `json.error_codes` list carries the complete current vocabulary and is checked against the generated error schema.

If install execution fails after planning, JSON mode still emits exactly one error envelope. `partial_install_failure` details include ordered installed-package outcomes, the failed and skipped packages, a typed partial-install status, trace identity, a phase-specific `failure_code`, and cleanup results.

Exit status follows the error class:

- `2` for syntax, invalid scoped help, unsupported options, and invalid option combinations;
- `1` for confirmation and runtime failures;
- `130` for typed interruption;
- `0` for success.

### NUL

NUL output emits package names separated by `\0` where supported. It is for shell pipelines, not rich structured data.

### Global option placement

Shared output and safety options are true global options. They have the same meaning before or after a command or nested subcommand:

```sh
glu --json status
glu status --json
```

A command rejects shared options it does not support instead of silently ignoring them.

### Summary, all, and tree

Dependency-aware query commands use progressive disclosure:

- default output shows the useful boundary or summary;
- `--all` expands the complete graph, flattens it, and deduplicates by stable package identity;
- `--tree` expands the same complete graph while preserving topology;
- combining `--all` and `--tree` is equivalent to `--tree`.

For `list`, the default boundary is the packages in `glu.json`; `--all` lists every installed package, and bare `--tree` renders the complete installed forest. Explicit `--declared --tree` filters out components unreachable from declared roots while retaining the dependencies needed to show each selected tree. For `deps` and `uses`, the default boundary is the immediate dependencies or dependents. For `why`, it is the declared root cause or causes that keep the queried package installed. Tree views show the complete connecting paths. Named query trees elide the already-named target while retaining branch markers from that hidden root; a dependency leaf reports `No dependencies.`. Forward dependency text and NUL output preserve the exact selector recorded on each edge, including aliases and old names.

JSON tree output preserves structure as data rather than exposing box-drawing text as the contract. Named dependency-query results carry `target` separately; graph roots and node depths are relative to the elided target. JSON and NUL follow the same default, all, and tree scopes as human output. Node-map keys are concrete package IDs, nodes include stable package keys and canonical names, and edges include their exact `requested_as` selector plus whether reverse traversal produced the edge. Flat dependency records retain package key, concrete package ID, and edge selector too. List-like JSON results are object-shaped so their scope, view, and future metadata can evolve without changing the result root type.

## Output ownership

The CLI owns final stdout, stderr, diagnostics, and exit status. Client operations return typed results. During execution they can emit typed lifecycle events and notices to an invocation-scoped sink. Human mode renders those events, while machine protocols use a silent sink. Client code does not select JSON, NUL, plan, or human rendering.

The internal postinstall worker is the only client path allowed to write process output directly. Its parent captures that output and relays it as typed notices, so worker output cannot corrupt a JSON result stream.

## Plan mode

Mutating commands that support plan mode compute the same state transition as execution, then stop before mutation.

Plan output shows the meaningful transition: install, update, reinstall, promote, rename, remove, keep, satisfy, download size, and confirmation requirement where relevant. In flat human install, update, and reinstall plans, bold names are exactly the resolved roots selected by the invocation; dependency depth metadata does not control emphasis. Isolated packages are annotated without adding warning noise to global packages. Package records include exposure plus local-state and impact annotations when known: `installed`, `linked`, `declared`, `deactivated`, `direct`, `transitive`, `cached`, `download_bytes`, and receipt-backed `installed_bytes`. `glu cleanup --plan` lists package names for cached downloads that match installed-receipt metadata, summarizes unassociated downloads, and reports total reclaimable bytes. Removal plans summarize exact package-default files that would be removed or retained; `--verbose` and JSON expose the paths. `glu purge --plan` lists every installed package, reports known reclaimable installed bytes, says whether `glu.json` would be removed or preserved, and includes the same configuration cleanup summary.

Plan mode is a read-only boundary between decision and execution. Recovery cleanup, lock-protected mutation, and package changes happen only on the execution side. Install and update plans preserve their dependency graph when `--tree` is selected.

### Update scopes

Update has three deliberate scopes:

- `glu update <package...>` updates the named declared roots and changes dependencies only when required for satisfaction;
- bare `glu update` applies that root-update behavior to every declared root;
- `glu update --all` also reconciles every package in the declared roots' dependency closure to the registry-selected release.

Normal root updates keep an older dependency when it satisfies every active installer-root context. Each root's complete selected-bottle requirement map applies throughout that root's topology closure, including below satisfied intermediate packages. They still install newly required or insufficient dependencies and remove dependencies dropped by the updated roots. `--all` is the explicit request to update satisfying dependencies too. Exact selected releases with matching persisted package facts are not repoured.

The outdated endpoint supplies staleness and presentation data, but does not gate reconciliation. Resolve remains authoritative for changed topology, provider identity, and package facts.

## Confirmation model

`--yes` approves the computed plan. It does not imply `--force`, `--all`, `--dependents`, or any other broadening behavior.

Commands ask for confirmation when the plan is broad by nature or removes more than the user directly named. Cache cleanup always asks when cached downloads are present. Purge always asks when it would remove an installed package or `glu.json`; `--keep-declaration` changes only the declaration part of that computed plan. Unchanged, uniquely owned package defaults are part of ordinary removal and need no extra approval. Attributable modified configuration is preserved unless the user accepts a separate default-no prompt or supplies `--remove-config`; non-interactive modified cleanup requires `--remove-config --yes`, and `--yes` alone never broadens configuration cleanup. At an interactive prompt, `Y` proceeds and `N` or Escape cancels immediately; Enter accepts the displayed default. Declining optional modified-file cleanup still removes the package and preserves those files. Cancellation of the package mutation itself is a normal successful exit and does not render an error. In non-interactive use, a required confirmation refuses and points at `--yes` instead of choosing a default.

This keeps safety independent from parser shape. New flags must not weaken confirmation semantics.

## Online and offline answers

Some read-only questions can be answered from local receipts or from the registry.

`deps` is the main example:

- installed packages answer from receipts by default;
- not-installed packages resolve from the registry;
- `--online` forces the registry answer.

These sources answer different questions. Output makes the source clear when it matters and does not silently mix local and registry data in one answer.

`info` reports the registry package's exposure policy. Human output says `global` or `isolated`
and explains isolated policy when a reason is available. JSON carries the same source-neutral
`exposure` object. Exposure policy is distinct from whether an installed package was deactivated
by the user. Install, update, and reinstall plans and results carry the same policy. After a
successful human mutation, isolation notices are limited to resolved requested roots, or declared
roots for updates; isolated transitive dependencies remain quiet. Flat list JSON also uses
`exposure` rather than a source-specific boolean.

## Short flag composition

Short flags compose when the command supports those flags:

```sh
glu ls -ajt
```

This must have the same semantics as the expanded long-form flags. Short composition is convenience, not a separate behavior mode.

## Help JSON contract

`glu help` is the primary discoverability contract. It shows concise Clap-generated usages, aliases, default scopes, command-specific options, mutation and confirmation behavior, and supported modes. `glu help --json` exposes the same command model to scripts.

The first public help-manifest contract uses `schema_version: 1`. The version remains 1 throughout the first release; a later incompatible contract change must increment it.

The manifest contains:

- commands, nested commands, aliases, arguments, and examples;
- each command's supported output protocols;
- stable error codes and global conventions; and
- explicit result schema identities.

Default help JSON omits generated schemas to keep command discovery compact. Add `--schemas` when strict validation or code generation needs Draft 2020-12 schemas:

```sh
glu help --json --schemas
glu help install --json --schemas
```

Top-level schema output includes every public result schema. Scoped schema output includes only the selected command tree's result schemas plus the help-manifest and error-envelope schemas. Optional properties describe values omitted from serialized output; required nullable properties describe fields that are always present and may contain `null`.

Help JSON is wrapped in the standard success envelope with canonical command identity `help`.
